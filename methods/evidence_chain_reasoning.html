证据链推理方法 — 方向三详细展开

肝病知识图谱核心方法贡献之一
创建日期: 2026-05-08 最后更新: 2026-05-11 (Meta-Template v1.0 设计完成) 状态: ✅ Layer 1 设计完成 (等待 Layer 2)

1. 问题定义：为什么需要证据链推理？

1.1 当前知识图谱的”黑箱”问题

现有的知识图谱能回答”是什么”的问题：

  • Q: “TP53 与肝癌相关吗？” → A: “是的，有关系”

但临床医生和科学家需要的不是这个，而是：

  • Q: “TP53 为什么与肝癌相关？有什么证据？”
  • → A: “基于3篇文献（PMID: xxx, yyy, zzz），其中1篇是2023年的临床试验，表明TP53突变在肝细胞癌中发生率约30%……”

关键洞察：知识图谱的用户需要的不是”关系”（Relationship），而是”叙事”（Narrative）——一个从证据到结论的可追踪路径。

1.2 与场景层的关系

  • 临床场景层解决的是”用户的思维路径 vs 图谱的拓扑结构”之间的鸿沟
  • 证据链推理解决的是”图谱输出的结果 vs 用户需要的决策依据”之间的鸿沟

两者互补：场景层把用户需求翻译成图谱查询，证据链把查询结果翻译回用户可理解的推理过程。

1.3 知识图谱的定位转变

在我们的架构中，知识图谱不再是”推理引擎”，而是作为数据源存在。证据链推理是一个独立系统，知识图谱只是其多个数据源之一（与其他数据源如文献数据库、临床数据集并列）。

2. 证据链的定义

2.1 什么是证据链？

证据链是一个有向无环图（DAG），其中：

  • 节点 = 证据项（文献引用、数据库记录、本体定义、临床数据）
  • 边 = 推理关系（支持、反对、条件触发）
  • 起点 = 用户输入（症状、基因名、疾病名）
  • 终点 = 推理结论（诊断建议、分子机制假设、治疗方案）

2.2 证据类型

证据类型来源可信度示例
文献证据PubMed高（经同行评议）“XXX 研究表明 YY 基因与肝癌相关”
本体证据HepatoOntology高（专家定义）“肝硬化是肝癌的危险因素”（is-a 关系）
关联证据CTD / DisGeNET中（统计关联）“ZZZ 化学物质与肝癌有统计关联，p<0.05”
临床证据临床数据集高（真实数据）“患者队列中，AFP>400 对 HCC 诊断敏感性为 80%“

2.3 推理模式

模式一：演绎推理

前提: 所有肝细胞癌(HCC)患者中约70% AFP升高（文献证据）
事实: 该患者AFP升高
结论: 该患者可能患有HCC（置信度: 70% × 证据质量权重）

模式二：溯因推理

观察: 患者AFP升高 + 肝脏超声发现结节
候选解释1: 肝细胞癌
候选解释2: 肝内胆管癌
候选解释3: 肝腺瘤
最优选择: 结合更多证据（乙肝病史、增强CT模式）缩小范围

模式三：类比推理

已知: 索拉非尼对HCC有效，机制是抑制VEGFR/PDGFR
新观察: 新药物AA与索拉非尼结构类似
推论: 新药物AA可能对HCC有效

模式四：时序推理

时序1: 患者长期HCV感染
时序2: 发展到肝硬化（发病后10年）
时序3: 诊断HCC（发病后20年）
推理: HCV感染→肝硬化→HCC是合理的疾病进展路径
           ↑ 需要文献证据支持每一步的关联

3. 方法设计：三层模板架构

本方案吸收自 Kimi 分析建议，结合我们的证据链引擎设计。

3.1 设计原则

  1. 模板不携带领域事实 → 领域事实由知识图谱动态供给
  2. 推理拓扑与领域知识分离 → 模板只引导推理方向
  3. 运行时动态绑定 → 通过插件机制实现模板到实例的绑定

3.2 三层模板架构

┌────────────────────────────────────────────────────────┐
│   Layer 1: Meta-Template (元模板)                        │
│   ───────────────────────────────────────────────       │

│   跨疾病通用，不包含任何领域特定内容                      │
│                                                         │

│                                                         │

3.3 机制说明

运行时驱动流程：

1. 用户查询 → 场景解析器识别场景类型

2. 选择 Layer 1 元模板（根据场景类型）
   └─ e.g. "诊断推理模板"

3. 加载领域插件（Domain Plugin）
   └─ 通过插件配置绑定 Layer 2 领域模板
   └─ e.g. "HCC 诊断配置插件"

4. 领域插件向知识图谱发送查询
   └─ 获取 Layer 3 实例数据（患者特定的 A-Box 事实）

5. 模板实例化，填充推理路径
   └─ 每一步从图谱/文献/临床数据收集证据

6. 生成可解释性输出
   └─ 带引用和置信度的推理报告

3.4 三种粒度的决策：三层架构解答了模板粒度问题

之前我们讨论的”粗粒度 vs 细粒度 vs 折中”问题，在三层架构下自然消解：

粒度问题三层架构的答案
粗粒度（诊断模板/治疗模板）→ Layer 1 元模板，跨疾病通用
中粒度（HCC 诊断模板）→ Layer 2 领域模板，通过插件配置
细粒度（具体患者的诊断链）→ Layer 3 实例模板，运行时动态绑定

实施策略：先定义 Layer 1 的元模板 DAG 拓扑（约 3-5 种推理拓扑），再创建 2-3 个”样板间”来验证 Layer 2 的领域配置格式的可表达性。

3.5 与 AliCoCo 方法的对比

维度AliCoCo 场景层我们的证据链引擎
核心问题搜索意图 vs 分类体系的匹配决策需求 vs 图谱结果的可解释性匹配
输出类型推荐结果列表带推理过程的结构化报告
模板结构扁平场景模板三层递进式模板（元→领域→实例）
领域知识绑定模板内建知识图谱动态供给（分离设计）
不确定性处理不涉及核心问题（证据有强弱、矛盾）
时序维度不涉及重要维度（证据时效性、事件顺序）

4.2 关键模块

模块A：场景解析器

  • 输入：用户查询（自然语言）
  • 输出：场景类型（诊断/治疗/机制探索/预后评估）
  • 方法：与临床场景层的接口对接，利用场景层解析结果

模块B：模板选择器

  • 输入：场景类型
  • 输出：对应的 Layer 1 元模板 DAG
  • 实现：预定义的推理拓扑库（约 3-5 种）

模块C：领域插件执行引擎

  • 输入：元模板 + 领域标识（如 “HCC”）
  • 输出：实例化的 Layer 2 配置
  • 关键：插件是参数配置的载体，不包含推理逻辑

模块D：多源证据聚合引擎

  • 对推理路径中的每一步，从多个数据源收集证据
  • 图谱查询：知识图谱中的实体-关系数据
  • 文献检索：PubMed 等文献数据库
  • 临床数据：患者队列数据（如有）
  • 本体验证：检查是否符合已知的分类/关系

模块E：证据融合评估引擎

证据分数 = Σ(证据项质量 × 证据类型权重 × 时效性因子) / 证据总数
  • 证据质量：期刊影响因子、引用数、实验类型（RCT > 队列研究 > 病例报告）
  • 证据类型权重：文献 > 本体 > 关联数据
  • 时效性因子：近 5 年文献权重更高

模块F：可解释性输出生成器

┌─ 推理结论 ──────────────────────────────────────┐

5. 实施策略

5.1 第一阶段：模板系统建设

  1. 定义 Layer 1 元模板（3-5 种推理拓扑）

    • 诊断推理模板
    • 治疗推理模板
    • 机制探索模板
    • 预后评估模板
    • 疾病关联模板

  2. 设计 Layer 2 领域配置格式

    • 确定配置项的结构化 Schema
    • 创建配置加载机制（Domain Plugin）

  3. 创建 2-3 个”样板间”

    • HCC 诊断配置
    • 肝癌治疗配置
    • HBV→肝硬化→HCC 机制探索配置

5.2 第二阶段：证据聚合

  1. 实现多源证据检索接口
  2. 实现证据质量量化机制
  3. 实现证据融合评估算法

5.3 第三阶段：交互与迭代

  1. 实现可解释性输出生成
  2. 半自动到交互式模式（系统推荐 + 用户修正）
  3. 与临床场景层集成测试

6. 开放问题（待探索）

  1. 推理路径的自动生成：Layer 2 领域配置是否需要支持动态推断，还是完全预定义？
  2. 证据质量的跨源对齐：不同数据源的证据质量如何统一量化标准？
  3. 矛盾证据的呈现策略：当不同来源证据结论相反时，如何呈现给用户？
  4. 领域插件的复用性：如何设计领域配置格式，使得不同疾病之间能复用部分配置？
  5. 评估方法：如何验证证据链推理的质量？用户实验？专家评审？回溯验证？

7. 参考工作

  • 开放证据链 (Open Evidence Chain)：类似的法律/科学证据推理框架
  • 生物医学推理系统：如 IBM Watson for Oncology 的证据回溯
  • 可解释 AI (XAI)：图神经网络的解释方法（GNNExplainer、PGExplainer）
  • Kimi 分析建议：三层模板架构（元模板-领域模板-实例模板），模板与领域知识分离

9. 与 TESG 的接口约定

更新日期：2026-05-11 来源：方向二（跨模态语义对齐）与方向三（证据链推理）合并讨论 状态：📋 约定已确定，待实现时对齐

9.1 模块关系

推理引擎（方向三）在上，TESG（方向二）在下。推理引擎调用 TESG 的语义查询接口。

┌─────────────────────────────┐
│    推理引擎（方向三）          │
│  Layer 1/2/3                │
│      ↓ 调用                   │
├─────────────────────────────┤
│    TESG 语义坐标系（方向二）    │
│  时序轴(T) / 因果轴(C) / 证据轴(E)│
└─────────────────────────────┘

9.2 核心原则：分层保留，按需融合

红线原则：TESG 的核心输出永远是分层语义棱镜（Semantic Prism），即 T/C/E 三个维度各自保留独立语义；融合只是上层调用的一个可选函数，且融合结果必须可拆解。

#原则说明
1分层是默认，融合是可选TESG 默认输出 T/C/E 各自的结构化语义；融合由上层按需调用
2融合必须可拆解任何融合查询返回 decomposition 字段，标注融合值来源比例
3冲突在融合前检测T/C/E 维度间的方向性冲突必须在融合层之前标记，不靠融合”抹平”
4维度查询优先于融合查询Layer 2 的 Domain Profile 主要使用分层查询，只在最终输出阶段可选融合

9.3 两类查询接口

TESG 应提供两类接口，推理引擎根据不同阶段选择调用：

A. 分层语义查询（推理引擎主要使用）

调用方：EvidenceCollector 和 ConflictResolution 节点。

B. 融合语义查询（推理引擎最终输出阶段可选调用）

调用方：InferenceEngine 和 ExplanationGenerator 节点（生成最终置信度和推理报告时使用）。

9.4 与 Layer 2 配置的协作

Layer 2 的 Domain Profile 中，evidence_query_builder 的证据维度应映射到 TESG 的分层查询接口：

Domain Profile 维度TESG 语义维度调用接口
literaturepubmed_miningquery_semantic_prism（E轴为主）
ontologyobo_semanticquery_semantic_prism（C轴为主）
associationassociation_networkquery_semantic_prism（E轴+C轴）
clinicalehr_semanticquery_semantic_prism（T轴+C轴）
综合评分—query_fused_semantic（可选）

9.5 降级策略

TESG 未实现时，推理引擎使用降级策略：

级别TESG 状态策略
Level 1完整实现调用 query_semantic_prism 获取分层语义
Level 2仅结构化标注使用 edge_semantic_facets 表中的静态标签，无动态融合
Level 3未实现纯规则驱动（基于 Layer 2 conflict_rules 配置）

降级粒度：每个查询独立降级。TESG 查询超时（如 5 秒）→ 自动降为 Level 2 → 记录降级事件。

8.2 DAG 拓扑（9节点）

                                            ┌─────────────────────────┐
                                            │  反馈: 证据质量不足      │
                                            │  EvidenceEvaluator →    │
                                            │  EvidenceCollector      │
                                            └──────────┬──────────────┘
                                                       │
[用户输入] → [ObservationParser] → [CandidateGenerator]
                ↓                           ↓
         [DifferentialRanker] ← [反馈: 冲突需临床信息]
                ↓                      ConflictResolution
         [EvidenceCollector] ←───────┐  ↑
                ↓                    │  │
         [EvidenceEvaluator] ────────┘  │
                ↓                       │
         [InferenceEngine] ─────────────┘
                ↓
         [ConflictResolution] ←── TESG时序语义查询
                ↓
         [ConclusionRanker]
                ↓
         [ExplanationGenerator] → [推理报告]

边类型：

  • sequential：主推理路径
  • feedback：回退路径（EvidenceEvaluator → EvidenceCollector，当质量阈值以下时触发）
  • feedback：回退路径（ConflictResolution → ObservationParser，当冲突需要额外临床信息时触发）

8.4 推理模式嵌入

Temporal（时序）ConflictResolution时序语义冲突检测（需 TESG）

8.7 图谱交互接口

定义了 4 个查询方法（由 Layer 2 Domain Profile 实现具体适配器）：

  • query_candidates(observations, ontology_scope) → 候选疾病列表（CandidateGenerator）
  • query_evidence(entity_pair, evidence_types, temporal_context) → 多维度证据面（EvidenceCollector）
  • query_temporal_semantic(entity_pair, disease_stage) → 时序语义向量（ConflictResolution / TESG 接口）
  • query_disease_hierarchy(disease_ids) → 疾病层级关系（ConclusionRanker）
