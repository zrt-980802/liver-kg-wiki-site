任务：设计 Layer 2 Domain Profile Schema（领域配置 Schema）

此任务属于肝病知识图谱项目 — 证据链推理引擎（方向三） 的一部分。 前置条件：Layer 1 Meta-Template DiagnosticAbduction_v1.0 已完成设计。 请阅读以下完整背景，然后完成具体任务。

一、项目背景（必读）

本项目是一个生物医学知识图谱项目，核心命题是弥合知识图谱构建者与使用者之间的认知鸿沟。

三大方法贡献：

方法状态说明
临床场景层✅ 设计完成把图谱的”网络结构”翻译成医生能理解的”场景化知识”
跨模态语义对齐🚧 待实现多源数据语义颗粒度差异的对齐与融合
证据链推理✅ Layer 1 完成把图谱输出的”关系”变成可追踪的”推理路径”（当前任务所在）

三者关系：跨模态对齐为底层（数据怎么融）→ 场景层为桥梁（需求怎么接）→ 证据链为上层（结果怎么用）。

二、证据链推理引擎的完整架构（必读）

2.1 三层模板架构（已确定）

项目采用了三层模板架构（Kimi 分析建议 + 项目组确认）：

层级粒度职责状态
Layer 1: Meta-Template粗粒度定义推理拓扑 DAG，跨疾病通用✅ 已完成 (DiagnosticAbduction_v1.0)
Layer 2: Domain Template中粒度某类疾病的参数化配置，通过领域插件加载🚧 当前任务
Layer 3: Instance Template细粒度运行时动态绑定，图谱查询实例化❌ 待 Layer 2 完成后启动

核心原则：

  • 模板不携带领域事实 → 领域事实由知识图谱动态供给
  • 推理拓扑与领域知识分离 → 模板只引导推理方向
  • Layer 2 是 Layer 1 与 Layer 3 之间的桥梁 → 通过插件机制注入

2.2 完整推理流程

用户查询
    → 场景解析器识别场景类型
    → 选择 Layer 1 元模板（根据场景类型）
    → 加载领域插件，绑定 Layer 2 Domain Profile
    → 领域插件向知识图谱发送查询，获取 Layer 3 实例数据
    → 模板实例化，填充推理路径
    → 每一步从图谱/文献/临床数据收集证据
    → 证据融合评估（质量 × 权重 × 时效性）
    → 生成可解释性输出（带引用和置信度的推理报告）

2.3 证据类型

证据类型来源可信度基准
文献证据PubMed高（经同行评议）
本体证据HepatoOntology / OBO高（专家定义）
关联证据CTD / DisGeNET / STRING中（统计关联）
临床证据EHR 临床数据集高（真实数据）

三、Layer 1 Meta-Template 概览（前置条件）

当前已经完成设计的元模板 DiagnosticAbduction_v1.0 包含以下 9 个节点：

3.1 DAG 拓扑

[用户输入]
    ↓
[ObservationParser] — 解析观察
    ↓
[CandidateGenerator] — 基于观察生成候选疾病
    ↓  (反馈边: 证据质量不足)
[DifferentialRanker] — 鉴别排序
    ↓
[EvidenceCollector] — 为每个假设收集多维度证据 ←——┐
    ↓                                                │
[EvidenceEvaluator] — 评估质量/时效性 ────────────────┘
    ↓
[InferenceEngine] — 加权融合
    ↓  (反馈边: 冲突需临床信息)
[ConflictResolution] — 检测证据冲突（需 TESG 接口）
    ↓
[ConclusionRanker] — 最终排序
    ↓
[ExplanationGenerator] — 生成推理报告

3.2 节点插件槽位

这是 Layer 2 Domain Profile 需要注入的地方——每个节点声明了对外部领域知识的依赖：

节点插件槽功能描述
ObservationParserobservation_extractor解析用户输入，提取结构化观察
CandidateGeneratorcandidate_generator基于观察生成候选疾病列表
DifferentialRankerranking_strategy对候选疾病进行鉴别排序
EvidenceCollectorevidence_query_builder为每个假设构建证据查询
EvidenceEvaluatorevaluation_criteria评估证据质量、时效性、一致性
InferenceEnginefusion_weights综合评估的加权策略
ConflictResolutionconflict_rules冲突识别与处理规则
ConclusionRankerconclusion_formatter最终排序规则
ExplanationGeneratorreport_generator推理报告生成模板

3.3 图谱交互接口（由 Layer 2 实现具体适配器）

Layer 1 定义了接口签名，Layer 2 负责实现与具体知识图谱/数据源的对接：

  1. query_candidates(observations, ontology_scope) → 候选疾病列表
  2. query_evidence(entity_pair, evidence_types, temporal_context) → 多维度证据面
  3. query_temporal_semantic(entity_pair, disease_stage) → 时序语义向量
  4. query_disease_hierarchy(disease_ids) → 疾病层级关系

四、当前任务：设计 Layer 2 Domain Profile Schema

4.1 任务目标

设计一套领域配置格式（Domain Profile Schema），让 Layer 1 的 DiagnosticAbduction_v1.0 元模板能够挂载到具体的疾病诊断场景上。

通俗来说：Layer 1 定义了”怎么推”，Layer 2 要定义”推什么”——对于某类疾病（如 HCC），你需要告诉元模板：

  • 哪些观察值可以触发推断？（AFP > 400？超声结节？）
  • 哪些疾病是常见候选？（HCC、ICC、肝腺瘤……）
  • 每种证据应该占多少权重？（文献 0.4、临床 0.3……）
  • 不同疾病间的鉴别要点是什么？
  • 证据冲突时怎么处理？

4.2 需要产出

请设计一个完整的 Domain Profile Schema，至少包含以下部分：

A. 配置结构定义

定义 Domain Profile 的整体数据结构。参考格式（YAML/Schema/JSON 均可）：

请为每一个插件槽定义其配置结构，包括：

  • 该配置的数据类型（数值、枚举、表达式、查询模板……）
  • 必需的字段 vs 可选的字段
  • 默认值（如果有）
  • 示例值

B. HCC 诊断的具体配置示例

以 HCC（肝细胞癌）为第一个”样板间”，给出一个完整的配置实例。这应包括：

  1. ObservationParser 配置：定义哪些临床观察可以触发 HCC 诊断推理

    • 如：AFP > 400 ng/mL、超声发现肝结节、乙肝病史……
    • 触发条件是什么样的组合逻辑？（AND/OR/权重和）

  2. CandidateGenerator 配置：定义候选疾病列表及激活条件

    • 如：AFP > 400 → HCC (权重0.7), ICC (权重0.2), 活动性肝炎 (权重0.1)
    • 本体驱动还是规则驱动？或是两者结合？

  3. EvidenceCollector 配置：每个证据维度的查询策略

    • 文献维度：查询什么关键字？使用什么文献数据库？
    • 关联维度：查询什么图谱路径？使用什么置信度阈值？
    • 临床维度：匹配什么患者队列？匹配条件是什么？

  4. InferenceEngine 配置：四类证据的融合权重

    • 文献权重、本体权重、关联权重、临床权重分别是多少？
    • 是否支持权重的动态调整（如根据患者特征调整）？

  5. ConflictResolution 配置：冲突处理规则

    • 什么情况下认为是”时序语义翻转”？（如 TGFB1 早期保护/晚期促癌）
    • 冲突时如何处理？标记人工判断？降低置信度？保留双方证据？

  6. 输出格式模板：HCC 诊断报告的特定格式

    • 是否需要包含 BCLC 分期？LI-RADS 分类？
    • 推荐检查项的优先级？

C. Schema 的通用性设计

Layer 2 的核心价值在于可复用性。请考虑：

  1. 疾病无关的部分 vs 疾病相关的部分：哪些配置字段是所有肝病诊断共享的？哪些是 HCC 特有的？
  2. 配置继承机制：是否可以定义一个”肝病诊断基础 Profile”，然后 HCC、HBV、肝硬化等疾病继承并覆盖特定字段？
  3. 跨疾病复用性评估：这个 Schema 能否用于 ICC（肝内胆管癌）、肝腺瘤、肝硬化等其他肝病？需要改动哪些部分？
  4. Layer 1 的局限性反馈：目前的 DiagnosticAbduction_v1.0 的 9 节点结构是否足够支持 HCC 诊断场景？如果有不足，是反馈回 Layer 1 修改，还是 Layer 2 用配置来弥补？

D. 与跨模态语义对齐（TESG）的接口定义

Layer 2 Domain Profile 需要与底层的跨模态语义对齐层对接。请定义：

  1. 证据维度的语义映射：Domain Profile 中定义的”文献证据""关联证据”如何映射到 TESG 的语义维度？
  2. 时序上下文传递：Domain Profile 如何告诉 TESG 当前诊断处于疾病的哪个阶段？
  3. 冲突证据的语义查询：当 Domain Profile 检测到证据冲突时，如何调用 TESG 的时序语义查询接口？
  4. 如果 TESG 尚未实现，降级策略：没有 TESG 时，Domain Profile 应该怎么退回到纯规则驱动的推理？

E. 验证标准：怎样算设计好了？

请提出 3-5 条验收标准。例如：

  1. 配置可解析性：定义的 Schema 能否被解析成结构化的 JSON/YAML 对象？
  2. 样板间可运行性：给定完整的 HCC 配置，能否手动推演出一条完整的推理路径？
  3. 跨疾病迁移测试：能否只用一天时间，把 HCC 配置改写成 ICC 配置？
  4. 动态数据源测试：当图谱中的数据更新时（如新文献报告 AFP 敏感性从 70% 变为 75%），仅更新图谱而不改配置，推理结果是否自动变化？

4.3 需要特别注意的设计原则

  1. 配置不写死领域事实：任何具体的数值（AFP > 400）、具体的疾病名称（HCC）、具体的文献引用（PMID:12345678）都不应该出现在 Schema 定义中。它们应该在配置实例中出现，Schema 只定义”数据应该放在什么位置”。

  2. Schema 是可扩展的：未来添加新的疾病（如从 HCC 扩展到 ICC、HBV）时，不需要修改 Schema 定义，只需要创建新的配置实例。

  3. 显式的默认值和回退策略：每个配置字段都应说明：如果未提供，默认行为是什么。

  4. 人与机器都可读：配置格式既应该能被程序解析执行，也应该能被人类（临床医生/知识工程师）理解并手动编辑。

4.4 输出格式

请以结构化的 Markdown 文档输出，包含上述 A-E 所有部分。如果能同时提供 YAML/JSON Schema 形式的 Domain Profile Schema 定义（一个 .yaml 或 .json 文件），将非常有帮助。

最终产出应为两个文件：

  1. schemas/domain_profile_schema.md — 完整的设计文档（人读）
  2. schemas/domain_profile_schema.json 或 schemas/domain_profile_schema.yaml — Schema 定义（机读）
