任务：设计 Layer 3 推理执行引擎（Instance Template + Reasoning Engine）

此任务属于肝病知识图谱项目 — 证据链推理引擎（方向三） 的一部分。 前置条件：Layer 1 推理拓扑层 + Layer 2 领域配置层 均已设计完成。 请阅读以下完整背景，然后完成具体任务。

⚠️ 重要说明：本任务经过外部审查后修正了范围。 Layer 3 不是”模板”，它是第一个运行时系统。 产出分为两部分：Instance Data Schema（数据结构）+ Reasoning Engine Architecture（执行引擎）

一、项目背景（必读）

本项目是一个生物医学知识图谱项目，核心命题是弥合知识图谱构建者与使用者之间的认知鸿沟。

三大方法贡献：

方法状态说明
临床场景层✅ 设计完成把图谱的”网络结构”翻译成医生能理解的”场景化知识”
跨模态语义对齐🚧 待实现多源数据语义颗粒度差异的对齐与融合（TESG）
证据链推理✅ Layer 1 ✅ Layer 2 🚧 当前任务关系→可追踪推理路径（三层架构的最后一环）

二、三层架构修正（必读）

经审查，三层架构的命名和本质应修正如下：

层级建议命名本质状态
Layer 1推理拓扑层数据结构（DAG 定义）✅ DiagnosticAbduction_v1.0
Layer 2领域配置层数据结构（配置格式）✅ DomainProfileSchema_v1.0 + HCC 样板间
Layer 3推理执行引擎运行时系统🚧 当前任务

三者关系：

  • Layer 1 定义”路径”（推理拓扑 DAG）
  • Layer 2 定义”资源”（领域知识配置）
  • Layer 3 负责”运行”（调度执行、数据绑定、输出）

核心原则（贯穿三层）：

  • 模板/配置不携带领域事实：Layer 3 可以包含数据访问逻辑（表名、字段名、查询语句），但不能包含医学判断逻辑（不知道”AFP>400”的临床意义——那是 Layer 2 的配置）
  • 错误隔离：一个节点失败不应导致整个推理链崩溃
  • 可观测性：每个节点执行应有完整日志

三、前置条件概览

3.1 Layer 1 DAG 拓扑（9节点 + 2条反馈边）

[ObservationParser] → [CandidateGenerator] → [DifferentialRanker] → [EvidenceCollector]
                                                                           ↓
[ConclusionRanker] ← [ConflictResolution] ← [InferenceEngine] ← [EvidenceEvaluator]
       ↓                        ↑
[ExplanationGenerator]          └── 反馈边1: EvidenceEvaluator→EvidenceCollector（证据质量不足）
                                └── 反馈边2: ConflictResolution→ObservationParser（冲突需临床信息）

每个节点有一个 插件槽位（Layer 2 注入配置）。

3.2 Layer 2 配置加载方式

Layer 3 需要加载 YAML 配置并解析：

  • 支持 extends/overrides 配置继承（实例化时预编译为运行时对象）
  • 将 SQL 查询模板编译为可执行查询
  • 验证配置合法性（对照 JSON Schema）
  • 启动时预编译，避免每次推理都解析 YAML

3.3 运行时数据流

[用户输入]
    ↓
Layer 3 运行时引擎
    │
    ├─ 1. 加载 Layer 2 配置（启动时预编译）
    ├─ 2. 根据 observation_extractor 解析用户输入 → 查询图谱获取数据
    ├─ 3. 根据 candidate_generator 生成候选疾病列表
    ├─ 4. 对每个候选调用 evidence_query_builder 收集多维证据
    ├─ 5. 根据 evaluation_criteria 评估证据质量
    ├─ 6. 根据 fusion_weights 加权融合
    ├─ 7. 根据 conflict_rules 检测冲突
    ├─ 8. 根据 conclusion_formatter 输出排序结果
    └─ 9. 根据 report_generator 生成最终推理报告

四、当前任务：设计 Layer 3 推理执行引擎

4.1 任务目标

设计一个可在真实数据库上运行的推理执行引擎，使得：

  1. Layer 1 的抽象 DAG 和 Layer 2 的静态配置能够在运行时绑定具体数据并执行
  2. 用户查询 → 图谱查询 → 证据收集 → 推理路径填充 → 输出结果 的全链路打通
  3. 优先基于现有 SQLite 表实现一个最小可运行版本（MVP），再规划扩展路线

4.2 产出物

本次任务产出 两个文件：

文件内容定位
schemas/instance_data_schema.md运行时数据结构定义数据结构
engine/reasoning_engine_architecture.md执行引擎架构设计（含伪代码）系统设计

4.3 需要产出的内容

A. 运行时数据结构（Instance Data Schema）

定义 Layer 3 的核心数据结构，这是在引擎中流转的数据模型：

  1. Session（推理会话）

    • 一次推理从头到尾的完整上下文
    • 包含：session_id, profile_id（加载的配置）, status, created_at, input（用户查询）, context_cache（节点间传递的中间结果）, output
    • 支持序列化/反序列化（可存储、可复现）

  2. ExecutionPlan（执行计划）

    • 根据 DAG 拓扑生成的节点执行顺序
    • 包含：steps（有序节点列表）、parallel_groups（可并行节点）、feedback_loops（回退路径定义）、max_iterations（防止无限循环）
    • 关键：必须处理反馈边形成的有向循环图（主路径拓扑排序，反馈路径条件触发 + 最大迭代次数上限）

  3. StepResult（节点执行结果）

    • 每个 DAG 节点的执行输出
    • 包含：node_id, status, input, output, evidence_list, confidence, execution_time_ms, error（如果有）
    • 支持缓存，供反馈边复用

  4. InferenceResult（推理最终结果）

    • 对应 Layer 1 输出 Schema 的具体化
    • 包含：conclusion, confidence, differential_diagnosis, evidence_chain, uncertainties, conflicts, recommendations, provenance

B. 执行引擎架构（Reasoning Engine Architecture）

这是本次任务的核心产出。请设计一个可执行的引擎架构：

B1. DAG 执行调度器

  • 拓扑排序：对 DAG 主路径进行拓扑排序
  • 并行组：识别哪些节点可以并行执行（如 EvidenceCollector 可以同时为多个候选疾病收集证据）
  • 反馈处理：检测反馈条件 → 中断当前路径 → 回退到指定节点重新执行 → 设置最大迭代次数（如 3 次）
  • 状态管理：记录每个节点的执行状态（pending / running / completed / failed / skipped）

B2. 节点执行器（Node Executor）

每个 DAG 节点对应一个执行器，接口定义：

需要至少为以下特殊节点给出伪代码/架构设计：

  • ObservationParser：如何将配置中的 trigger_conditions 编译为 SQL 查询？
  • CandidateGenerator：如何结合 ontology_driven 和 rule_driven？
  • EvidenceCollector：如何并发查询多个证据维度？如何聚合结果？
  • InferenceEngine：如何根据 fusion_weights 进行加权计算？
  • ConflictResolution：如何处理反馈边？

B3. 插件加载机制

  • Layer 2 的 9 个插件槽如何在运行时加载？
  • 插件接口定义（每个插件需要实现的方法）
  • 降级机制：如果插件实现不可用（如implementation: "ml_model"但模型未部署），使用 fallback 配置

B4. 图谱查询适配器

  • 查询编译器：将 Layer 2 配置中的 SQL 查询模板 → 参数绑定 → 可执行语句
  • 数据源适配器：统一接口对接 SQLite，预留 PostgreSQL / API 接口
  • 结果转换器：数据库原始行 → 标准化的 EvidenceFacet（属性映射、转换函数）
  • 连接管理：连接池、查询超时、重试

这是 Kimi 审查指出的关键风险。Layer 2 HCC 配置中引用了很多当前不存在的表。

请审计当前数据库，并为每个查询标注可用状态：

分层处理策略：

  1. ✅ 已可用：直接用现有表实现
  2. 🚧 Mock 可用：当前表不存在，但可以用现有表近似模拟（如用 edge_semantic_facets.normalized_confidence 近似 biomarker_diagnostics.specificity）
  3. ❌ 外部依赖：需要 PubMed API、EHR 接入等，标记为”未来扩展”

核心问题：只基于现有表（entities/edges/edge_semantic_facets），能跑通什么？ 请给出一个”最小可运行子集”的定义。

D. TESG 接口适配与降级

当前 TESG 由另一个 agent 设计，Layer 3 需要预留接口并实现降级：

  1. TESG 查询接口定义

    • query_temporal_semantic(entity_pair, disease_stage) 的输入/输出 Schema
    • 超时配置（如 5 秒）

  2. 三级降级策略的运行时实现

    • Level 1：完整 TESG（未来启用 — 切换 tesg_interface.enabled=true 即可）
    • Level 2：静态语义标签库（基于 edge_semantic_facets 的 normalized_confidence 实现简单冲突检测）
    • Level 3：纯规则（基于 config 中的 conflict_rules.rule_based）
    • 降级粒度：每个查询独立降级（TESG 查询超时 → 自动降级 → 记录降级事件）

  3. 与 Layer 2 配置的协作

    • 检查 tesg_interface.enabled 配置
    • 根据降级级别选择不同的 conflict_rules 执行路径

E. 结果持久化与回写

  1. 推理记录表 Schema

    • 存储每次推理的完整记录
    • 支持历史查询和分析（session 表、step_result 表）

  2. 推理结果隔离策略（Kimi 审查指出的关键问题）

    • ❌ 机器推理结果不能直接写入人工标注区
    • ✅ 隔离的”机器推理”命名空间
    • 回写数据必须标记 provenance: "machine_reasoning"，区分于人工标注

  3. 推理质量监控

    • 每个节点的执行时间记录
    • 需要人工复核的案例标记（conflict 标记、低置信度）
    • 人工反馈驱动改进的接口预留（用户纠正 → 更新配置或图谱）

F. 验证标准

请遵循 “先最小可运行，再逐步扩展” 的原则：

MVP 验收标准（必须满足）：

编号标准说明
V1端到端可运行给定用户输入，加载 HCC 配置，基于现有 SQLite 表输出完整推理报告（即使部分证据维度为空）
V2结果可复现相同输入和配置，多次运行产生一致的推理结果
V3配置可加载hcc_diagnostic_profile.yaml 能被正确解析为运行时配置，继承机制生效

扩展路线图（标注优先级，不要求全部实现）：

编号标准优先级说明
V4并行执行🟡 中架构支持并行，但 SQLite 下串行 10 个 ≤ 单次 10 倍
V5降级运行🟡 中TESG 不可用时自动降级为 Level 2
V6配置热更新🟢 低修改 YAML 配置后，无需重启服务即可生效
V7结果回写🟢 低高置信度结论回写到图谱的隔离命名空间

4.4 特别注意事项（来自审查反馈）

  1. 不要试图设计一个”完美引擎” — Layer 3 的核心产出是：

    • ✅ 运行时数据结构（Session / ExecutionPlan / StepResult 的 Schema）
    • ✅ 一个能跑的最小版本
    • ✅ 扩展路线图

  2. 数据源可用性矩阵是必须的 — 每个查询标注现有的/待扩展的/外部依赖的

  3. “模板不携带领域事实”的具体边界：

    • ❌ 不应出现："AFP>400 是 HCC 的强指标"（这是 Layer 2 的配置）
    • ✅ 必须出现："从 clinical_observations 表查 biomarker_name='AFP' 的记录"（这是 Layer 3 的数据访问逻辑）

  4. 反馈边处理 — Layer 1 的 DAG 包含反馈边，形成有向循环图。拓扑排序无法直接应用，需要：

    • 主路径：线性拓扑排序
    • 反馈路径：条件触发 → 中断 → 回退 → 重新执行 → 设置最大迭代次数（防止无限循环）

4.5 建议执行顺序

  1. 审计数据库 → 列出现有表结构，标注可用状态
  2. 设计运行时数据结构 → Session, ExecutionPlan, StepResult, InferenceResult
  3. 实现最小引擎 → 只支持主路径（无反馈边），只查询现有表
  4. 验证 MVP → 用 mock 患者输入跑通端到端
  5. 逐步扩展 → 反馈边 → TESG 降级 → 并行执行 → 结果持久化 → 配置热更新
